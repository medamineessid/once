## 2026-11-04 — B2: `close_application` and `PROCESS_TO_APPLICATION` are not in this tree

- Found (2026-11-04, B2, branch `b/b2-approval-panel`): task B2 asks for "chrome" in `ai/provider.py PROCESS_TO_APPLICATION` and for an explanation of how `close_application` matches a PID. Neither name exists anywhere in the repo. `ai/provider.py` contains only `AnalysisProvider`, `FakeAnalysisProvider`, `deterministic_demo_provider` and `MAX_INTERVIEW_TURNS`; `ai/analyze_recording.py` (also listed as owned) does not exist; there is no `CLOSE_APPLICATION`/close step kind in `StepKind`; the only close-like code is `controller/service.py::close_browser_sessions`, which closes isolated DevTools sessions and is unrelated.
- Default applied (fail closed, nothing invented): added `chrome` to `KNOWN_APPLICATIONS` (engine/workflow.py) and to `WindowsApplicationRegistry.resolve` (Program Files, Program Files (x86), `%LOCALAPPDATA%`; a missing install raises a plain-language `ExecutionError`). The desktop provider now launches Chrome with its own disposable `--user-data-dir` (`once-chrome-profile-<uuid>` under `%TEMP%`) and refuses a step that supplies `--user-data-dir` or `--profile-directory`. No close step kind and no `PROCESS_TO_APPLICATION` constant were added: a new mutating capability (terminating an application) needs approval semantics, a side-effect preview and a postcondition before it exists, and an unused mapping constant would be dead code while the analysis module it belongs to is absent.
- What a real `close_application` must do when someone builds it (design note only, NOT implemented and NOT tested): close by the exact `process_id` recorded in the launch step's evidence, never by window title, image name or "the newest chrome.exe"; re-check that the process still exists and that its image path equals the recorded executable before terminating; refuse when the PID is gone or the process is not the one we launched; and report refusal in plain language. Because the launch always uses its own `--user-data-dir`, Chrome cannot hand the command line to an already-running instance: a fresh profile guarantees a new browser process, so the recorded PID is ours. If a future launch were ever allowed on a shared profile, Chrome would forward to the existing instance, the launched PID would exit immediately, and any close-by-PID would either fail (PID gone) or, worse, kill a process we do not own - which is exactly why the profile switch is refused above rather than silently replaced.
- Needs owner: (a) where does the recorded-process -> registered-application mapping belong (`ai/analyze_recording.py` is absent; the recorder module that would consume it is unimplemented), and (b) should closing an application join `MUTATING_DESKTOP_KINDS` and the approval panel, or stay out of scope until replay postconditions exist?
